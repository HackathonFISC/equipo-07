## 2. CONTEXTO DEL PROYECTO

Nombre provisional: AguaIA.

Es un proyecto del Hackathon FISC AI Agents 2026, orientado a resolver problemas sociales reales de Panamá.

Reto elegido: Agua — Centro de coordinación agéntico para la crisis del agua en Panamá Oeste, especialmente Arraiján y La Chorrera.

Problema:
- Los ciudadanos reportan interrupciones de agua mediante mensajes, llamadas, imágenes o audios.
- Muchos reportes corresponden al mismo incidente.
- Algunas comunidades tienen mayor visibilidad que otras.
- Existen poblaciones vulnerables e instituciones críticas.
- Los recursos de distribución de agua son limitados.
- La coordinación debe ser justa, explicable y verificable.
- La solución futura debe poder planificar carros cisterna según capacidad, disponibilidad, rutas y horarios.
- El sistema debe permitir supervisión humana antes de ejecutar decisiones relevantes.

La aplicación debe evolucionar hacia un centro de operaciones con reportes ciudadanos, incidentes consolidados, priorización, planificación de recursos, mapas, notificaciones y auditoría.

IMPORTANTE: esta primera ejecución NO pretende implementar toda la solución final.

Se busca establecer una arquitectura sólida, una base funcional y un vertical slice que permita añadir requisitos y funcionalidades posteriores sin rehacer el proyecto.

El sistema NO debe reducirse a un chatbot.

## 8. ARQUITECTURA MULTIAGENTE

Implementa al menos tres agentes funcionales desde el inicio.

### Agente 1 — Ingesta y normalización

Responsabilidades:
- Procesar reportes ciudadanos en español.
- Extraer datos estructurados.
- Detectar información insuficiente.
- Normalizar descripciones.
- Identificar comunidad, duración y tipo de incidencia cuando la información lo permita.
- Transferir datos validados al siguiente agente.

Debe producir una salida estrictamente tipada.

No puede inventar ubicaciones, horarios, población afectada ni valores ausentes.

Cuando exista un modelo de IA configurado, utiliza el adaptador correspondiente para la interpretación semántica.

### Agente 2 — Verificación y consolidación

Responsabilidades:
- Revisar la información del reporte.
- Consultar incidentes existentes mediante herramientas controladas.
- Detectar posibles duplicados.
- Asociar reportes a incidentes existentes cuando exista evidencia suficiente.
- Crear un incidente nuevo cuando corresponda.
- Marcar incertidumbre y casos que requieren revisión humana.
- Registrar las razones de sus decisiones.

La deduplicación debe combinar reglas verificables con interpretación semántica cuando sea útil.

No permitas que la IA modifique libremente la base de datos.

### Agente 3 — Priorización y coordinación

Responsabilidades:
- Consultar incidentes verificados.
- Utilizar el motor determinístico de prioridades.
- Elaborar una propuesta explicable.
- Identificar los factores que justifican la prioridad.
- Solicitar aprobación humana.
- Registrar la decisión final.
- Preparar el resultado para futuras etapas de planificación.

El LLM no debe calcular puntuaciones arbitrarias.

Este agente debe consumir el resultado del algoritmo determinístico.

### Extensibilidad

Diseña el sistema para incorporar posteriormente:
- Agente de geolocalización avanzada.
- Agente planificador de cisternas.
- Agente de comunicación.
- Agente de análisis de imágenes.
- Agente de transcripción de audio.
- Agente de predicción o análisis histórico.
- Agente de auditoría.

Para cada agente implementado define:
- Responsabilidad.
- Entradas.
- Salidas.
- Estado que consume o modifica.
- Herramientas autorizadas.
- Condiciones de ejecución.
- Errores posibles.
- Estrategia de pruebas.

Los agentes deben representar responsabilidades operativas reales, no simplemente funciones rebautizadas como agentes.

Distingue claramente agentes, nodos de LangGraph, herramientas y servicios.

Implementa comunicación mediante el estado y las transiciones del grafo, sin acoplamientos innecesarios entre agentes.

Permite introducir agentes adicionales mediante composición de nodos o subgrafos.

Evita construir un registro dinámico de plugins complejo si no aporta utilidad inmediata.

## 9. ORQUESTACIÓN CON LANGGRAPH

Implementa un grafo funcional y verificable.

El flujo inicial debe ser aproximadamente:

Reporte recibido
→ Validación de entrada
→ Agente de ingesta
→ Agente de verificación
→ Consolidación de incidente
→ Agente de coordinación
→ Herramienta determinística de prioridades
→ Propuesta de decisión
→ Interrupción para revisión humana
→ Aprobación, rechazo o corrección
→ Persistencia de decisión
→ Finalización y trazabilidad.

Incluye transiciones condicionales para:
- Entrada inválida.
- Datos insuficientes.
- Incidente duplicado.
- Incidente nuevo.
- Errores recuperables.
- Revisión humana.
- Finalización.

La arquitectura debe contemplar estado tipado y persistencia de checkpoints.

Implementa el mecanismo necesario para que una ejecución pueda interrumpirse esperando aprobación humana y reanudarse sin comenzar todo el proceso nuevamente.

Utiliza identificadores estables de ejecución o thread_id y una estrategia de persistencia adecuada.

No mantengas una petición HTTP abierta indefinidamente mientras esperas una aprobación.

Evita ejecutar dos veces acciones con efectos secundarios durante reintentos o reanudaciones. Diseña operaciones idempotentes donde sea necesario.

No pretendas que un grafo dibujado equivale a un grafo realmente ejecutable.

## 13. VERTICAL SLICE OBLIGATORIO

El resultado debe permitir ejecutar una demostración completa.

Escenario:

1. Un ciudadano abre el frontend.
2. Envía un reporte de falta de agua.
3. El backend valida y guarda el reporte.
4. LangGraph inicia una ejecución.
5. El agente de ingesta normaliza la información.
6. El agente de verificación consulta incidentes existentes y determina si corresponde consolidar el reporte.
7. El agente de coordinación consulta el motor de prioridades.
8. Se genera una propuesta explicable.
9. La ejecución queda esperando una decisión humana.
10. Un coordinador revisa la propuesta desde el frontend.
11. El coordinador aprueba, rechaza o corrige con una razón.
12. LangGraph reanuda y registra la decisión.
13. Los estados actualizados se muestran en la interfaz.
14. Las trazas permiten revisar qué agentes y herramientas participaron.

Debe existir una acción real sobre la base de datos.

La revisión humana debe ser efectiva y persistida, no un botón visual que simplemente cambie texto en pantalla.

La aprobación debe estar protegida mediante un mecanismo de autorización proporcional al MVP. No expongas una operación administrativa completamente abierta.

No simules el despacho real de una cisterna ni confirmes una entrega de agua que no ha ocurrido.

Este vertical slice termina en una decisión de priorización aprobada y registrada. La planificación de rutas y distribución real queda para una fase posterior.

El flujo debe funcionar con datos de demostración reproducibles.
